## 1. Rules

| # | Rule |
|---|---|
| N1 | **A new action, `news`.** `TradeIntent.action` takes `"news"`: the person asks only for the news of one or more stocks ("Show the news for Tesla", "Show the news for TSLA", "What's Tesla's news?", "What's Tesla doing the last week?", "TSLA headlines for the past 3 days"). THE MODEL reads it (Jacob's rule that the model reads the request: no new cue-word filter decides it). The prompt (`prompts/account_manager_request.py`) gets one line for it, with made-up tickers like the others. A request that also asks to buy, sell, recommend or research ("what's Tesla's news, buy it if it's good") is NOT `news`: the old actions keep their meaning. |
| N2 | **What a `news` intent may hold.** `symbols` and/or `companies` (1 to `news.max_stocks`, 5), or a `topic` (searched in the stored news as a term, no company is looked for), and the window `news_days`. It may NOT hold orders, a budget, `each`, a count, an even split, `raise_funds`, `max_price`, `min_price`, typed shares (`shares_of`/`shares_each`): the validator refuses each with its reason, and the request is then one to clarify (entry 102). `as_direct_order` and the other programs that turn a `buy` into an `order` never touch a `news` intent. `describe()` says "show the news of Tesla for the last 7 days (nothing will be bought)". |
| N3 | **The window.** `news_days`, a whole number of days from 1 to `news.max_days` (90, the news fetch's own limit). A PROGRAM reads an explicit window from the words and wins over the model (a number of days moves no money, but it is a number and a program can read it): `news_window(typed)` for "last/past N day(s)/week(s)/month(s)" (7 and 30 days a week and a month), "last/past/this week" (7), "last/past/this month" (30), "today" (1), "yesterday" (2), "this year" is not read (over the limit). With nothing written the model's value, and with none either the default `news.default_days` (7). A window over the limit is cut to the limit and the user is told in one line ("the news is kept for at most 90 days: showing 90"). |
| N4 | **The route.** On every desk: `account_manager -> data_clerk -> END`. The Advisor, the Critic, the decision, the funds node and the Trader are never built into the path of such a run (`after_data_clerk` ends a `news` plan). Nothing reads or writes the account: no quote, no decision, no trade, no account write, no question in either mode. The security screen at the first node is unchanged. |
| N5 | **Naming the stocks.** The Data Clerk names them as it does for any request (`find_companies_of` with the exact lookup and the brand rule of entry 101: "Tesla" is TSLA, Tesla Inc; a typed ticker is the directory's). A name it cannot find is said in the pane with its reason; with no stock found and no topic the run stops and asks to clarify. |
| N6 | **The news, and only the news.** A new Data Clerk call `DataClerk.request_news(order, today)` (traced `data_clerk.request_news`): `verify_request`, then `ask(question, today, sweep=...)` exactly as `request_data` does, with two differences: the question asks for a SUMMARY of the news of the named stocks in the window, citing each item it uses (`_news_question`: the subject, the window, "call retrieve_news", at most `news.top_k` sources, 12), and the sweep searches the NEWS corpus only (no press releases, no filings, no filing evidence). The answer, its references and its sources go on `order.data` as today (`attach_result`). The citation check is the Data Clerk's own, unchanged. |
| N7 | **Always fetch the latest news (Jacob, 2026-11-23: *"Always fetch the latest news. Its too important to use stale news. It should be quick since its a direct API call anyways"*).** A news run fetches the NEWS of each named stock for the window before it searches, WHATEVER the run's fetch box says (`DataClerk.refresh_news(symbols, days)`: the same `fetch_news` tool; no bars, no press releases, no filings). The Data Clerk of a news run is built with `allow_fetch` for that reason. The guards stay: the Proving Ground's bound day refuses (nothing is fetched while a past day is bound), and a fetch that FAILS or is refused does not stop the run: the stored news is searched and the pane says so plainly ("could not fetch the latest news (reason): showing the stored news"), `fetched: false`. A topic is never fetched for (there is no symbol). The box's meaning for every other request is unchanged. |
| N8 | **What is shown.** `views.news_view(order, plan)` (pure) is the ONE shape the page and the session read: `{stocks: [{symbol, company}], not_found: [{typed, reason}], topic, days, fetched: bool, summary, items: [{number, headline, publisher, date, url, symbols, sentiment, cited}], problems, notes, no_supporting_text}`. One item per ARTICLE (chunks of one article are joined by their article id; its number is the first chunk's), the cited items first, then the rest, each group newest first. The summary is the Data Clerk's answer, passed through the same redaction door as the page's last message (`AccountManager.tell_user`'s door: secrets and other account numbers). No item is invented: an item is a source on the order. |
| N9 | **The page: a News pane.** A live or replayed run emits a new event `news` carrying `news_view`. The right column gets a TOGGLE (Jacob: *"Can toggle the pane to show both"*): two buttons at its top, **News** and **Work order**, switch between the **News** card (`ui/src/components/NewsPanel.tsx`) and the work order table with the recommendation panel. A news run selects News when its `news` event arrives; any other run selects Work order when it starts; the user can switch at any time and the other view keeps its content (the last news stays viewable during and after a recommendation run, until the next news run replaces it). With no news yet the News view says "Ask for a stock's news, e.g. \"What's Tesla doing the last week?\"". The News card has: the stocks and the window in its header ("TSLA · Tesla Inc · last 7 days · stored news" or "· fetched now"; a failed fetch is said in the header), the summary as plain text whose `[n]` marks link to the item with that number, then the items (headline as a link to its url, opened in a new tab with `rel="noopener noreferrer"`, publisher, date, the stock, cited or not), then the problems and notes. Text only: no HTML from the news is rendered (no `dangerouslySetInnerHTML`). The pipeline shows Account Manager and Data Clerk only. The run's last line (`finished`) is `status: "news"`, headline "The news of TSLA for the last 7 days", no trade, the portfolio unchanged. The Mode switch, Strict, Neutral, Ignore Critic and Always raise funds change nothing on such a run. |
| N10 | **The session.** `python -m prometheus.application.session` prints, for a `news` run, the stocks, the window, the summary and the numbered list (headline, publisher, date, url), and nothing about decisions, trades or the use of money. `--save` writes the request, the intent, the path and the order WITH its `data` (the news is the result). A news run is NOT saved to `data/proving/sessions/` (it has no recommendation to score). |
| N11 | **Nothing else changes.** Every other action, route and printed line is as it was; every existing test passes with no expected value changed. No size limit, risk rule or liquidity rule (entries 91, 93, 94). |

## 2. What changes, module by module

- `configs/account_manager_v1.json`: a section `news` with `default_days` 7, `max_days` 90, `max_stocks` 5, `top_k` 12 (and its loader).
- `prometheus/agents/account_manager/intent.py`: `"news"` in `action`, the field `news_days: int | None` (left out of the dump when None, like the fields of entry 138, so the Proving Ground's research-cache keys do not change), the validator of N2, `news_window` (N3), `describe`/`what`/`as_request` for `news`, and wherever `parse_intent`'s known keys are listed.
- `prometheus/prompts/account_manager_request.py`: `"news"` in the action line, `news_days` in the JSON shape and the RETRY line, and one bullet for it (made-up tickers).
- `prometheus/agents/data_clerk/data_clerk_agent.py`: `request_news`, `_news_question`, `refresh_news`, and a news-only sweep spec (a parameter of `_sweep`, e.g. the corpora to sweep and whether to read filing evidence, defaulting to today's behaviour).
- `prometheus/langgraph/desk.py`: `read_text` builds the news order and plan for `intent.action == "news"` (`action_type="search_news"`, `source="news"`, `since_days=news_days`, `top_k` from the config, `live=fetch`, no case, no price limits); the `data_clerk` node, for a news plan, names the stocks (a topic skips that and is the order's subject as a term), fetches the news per N7 and calls `request_news`; `after_data_clerk` ends a news plan (N4). Update the module docstring's graph picture.
- `prometheus/application/web/views.py`: `news_view` (N8), and `run_verdict` for `action == "news"`. `desk_run.py`: emit `news` after the data_clerk node of a news run and skip the decision, trade and money blocks in `_finish`. `emitter.py`: the `news` event. `replay.py`: replays it from a capture that has it. `app.py`: nothing new in the request body.
- `prometheus/application/session.py`: N10.
- `ui/src/api/types.ts` and `events.ts` (the `news` event), `ui/src/state/` (the run's `news`), `ui/src/components/NewsPanel.tsx` (N9), `App.tsx` (the right column), the styles in `ui/src/styles/` in the page's existing look.
- `docs/design_choices.md` entry 149 (problem, decision, alternatives, consequences); `AGENTS.md` one sentence; `HowToRun.txt` one example; `README.md` if it lists the actions.

## 3. Tests (real data; no stand-in agents in new tests)

- `tests/fixtures/session_real/news_request_forms.json`: the REAL model's replies to about a dozen news requests (Jacob's four forms, "TSLA headlines for the past 3 days", "news on Apple and Microsoft this month", a theme "news about quantum computing", and three that are NOT news: "what's Tesla's news, buy it if it's good", "should I buy Tesla?", "buy 5 shares of TSLA"), captured once with the capture script the earlier form fixtures used. `tests/test_news_view.py` checks each parses to the expected action, stocks and window, and that the program's window wins.
- The validator of N2, each refusal once (no boundary repeats, entry 90).
- The route: a news plan runs `account_manager` and `data_clerk` only (record the nodes of `stream(["tasks"])`), on the desk with the Critic and the Trader, and the account (a throwaway Postgres account) is unchanged.
- `request_news` and `news_view` on the real capture of N-capture below: the sweep searched news only, every item is a source on the order, articles are joined, cited first.
- The web: a replay of the capture emits `news`, `finished.status == "news"`, no `decision`/`trade` events. The UI: `NewsPanel` renders the summary, links each `[n]`, renders a headline with `<script>` as text, and `App` shows it in place of the work order table.
- The whole Python suite (the one deselected test as usual) and the UI tests pass with no existing expected value changed.
- **N-capture.** After the code is in, one REAL session under the standing yes for paid runs that test the desk. The run always fetches (N7), so ONLY with Jacob's yes for that fetch (it writes `news/TSLA.txt`); until then the capture is made with the fetch refused (the Data Clerk built without `allow_fetch`, a test-only switch of the session, never a page option), which also records N7's fallback: a throwaway account, Ask mode, `"What's Tesla doing the last week?"`, `--no-fetch --cleanup --save tests/fixtures/session_real/news_tsla_week.json`. Checked by a test (path is `account_manager`, `data_clerk`; the order has news sources only; the window is 7).
